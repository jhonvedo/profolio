Installation

macOS · Linux · WSL
curl -fsSL https://claude.ai/install.sh | bash
Windows · PowerShell
irm https://claude.ai/install.ps1 | iex
# alternative
winget install Anthropic.ClaudeCode

The native installer updates itself. There's also Homebrew (brew install --cask claude-code) and npm (npm install -g @anthropic-ai/claude-code, requires Node 22+).

Then, in the repo folder: claude → sign in with the organization's claude.ai account. For the IDE, install the VS Code extension (also works in Cursor) or the JetBrains plugin (Rider for .NET, WebStorm for Node). Both show diffs in the IDE's viewer and share your current selection with Claude.

Windows and .NET: Claude Code runs natively on Windows. If your tooling lives in WSL, install inside WSL and open the repo from there. For this course's sample hooks to work on native Windows you need Git Bash (which Claude Code uses for hooks) and jq.

The work cycle

1 · Explore

"Read the payments module and explain how a refund is processed. Don't change anything yet." Claude searches, reads and summarizes.

2 · Plan

Shift+Tab to Plan (or /plan). Claude investigates read-only and presents a plan. Correct it before approving.

3 · Implement

Approve the plan. Claude edits, runs the build and tests, and fixes things until they pass.

4 · Verify and wrap up

/diff to review, /code-review for a second look, and ask for the commit with a conventional message.

How to ask well

Vague

"Fix the refunds bug."

Specific

"Partial refunds fail when the order has a discount (issue #482). Reproduce the error with a failing test in RefundServiceTestsrefund.service.spec.ts, fix it without changing the public API and run the whole suite."

  • Give the success criterion: a test, a command that must pass, an expected output.
  • Reference files with @: @src/Payments/RefundService.cs (with autocomplete).
  • Paste images with Ctrl+V: error screenshots, designs, diagrams.
  • Correct early: Esc interrupts; type while Claude works and the message gets queued.

Permission modes

Before editing a file or running a command, Claude Code can ask for your permission. The mode decides how much it asks. It isn't a setting you choose once and forget: it's normal to switch modes several times during the same task, depending on the phase you're in.

How to switch modes

Three ways to choose the mode
# 1. During the session: Shift+Tab cycles through modes.
#    The active mode shows below the prompt.

# 2. At startup, from the terminal
claude --permission-mode plan

# 3. As the repo default, in .claude/settings.json
{ "permissions": { "defaultMode": "plan" } }

You can also type /plan followed by the task to go straight into Plan mode with that request.

default: asks the first time

Claude asks for permission the first time it wants to use each tool or command. When it asks, you have three options: approve just this once, approve and don't ask again for that command in this project, or decline and tell it what to do instead.

Example. You ask "run the payments module tests". Claude proposes dotnet test tests/Payments.Testspnpm --filter api test payments and waits. If you choose "don't ask again", it's saved as an allow rule and next time it runs without interrupting you.

Use it in a repo you don't know or while you're learning. Within a few days you'll have approved the usual commands and it'll barely ask.

plan: think before touching

Claude can read, search and analyze, but doesn't edit files or run commands that change anything. At the end it presents a plan and asks how to continue.

Example · Plan mode
# Shift+Tab until you see "plan mode on"
> Partial refunds fail when the order has a discount (#482).
  Find the cause and propose how to fix it.

# Claude reads RefundService, the tests and the discount calculation.
# Then it shows a numbered plan:
#   1. The discount is subtracted twice in CalculateRefund…
#   2. Add a test that reproduces #482…
#   3. Fix the calculation and run the suite…

# And asks how to continue:
#   · Yes, and auto-accept edits
#   · Yes, and approve each edit
#   · No, keep planning

If something in the plan doesn't convince you, choose to keep planning and correct it: "don't change CalculateRefund's signature, other services use it". Correcting a plan takes seconds; undoing code costs much more.

Use it for any change across more than one file, in code you don't know, and whenever the task is ambiguous.

acceptEdits: implement without interruptions

Claude edits files and uses basic file commands (creating folders, moving) without asking. Other commands, like tests, git or installing packages, follow the permission rules: if they aren't approved, it asks.

Example. You approved the #482 plan choosing "auto-accept edits". Claude writes the test, fixes the calculation and updates two more files without stopping. You watch each diff go by in the terminal or the IDE. If you see something you don't like, press Esc, tell it what to change, and it carries on.

Use it after approving a plan. Careful: not asking doesn't mean you shouldn't look. Review with /diff when it's done.

auto: long tasks with light supervision

Claude decides on its own what to approve, with a safety classifier that checks each action in the background and stops risky ones.

Example. "Migrate the 40 endpoints from controllers to Minimal APIs following the OrdersEndpoints pattern". It's long and repetitive; you don't want to approve 200 actions. In auto it moves forward while you do something else, and you review the result at the end.

Use it for long, well-defined work, ideally on a separate branch. If it doesn't show up when cycling with Shift+Tab, check with your plan's admin.

dontAsk: with nobody watching

Anything that would require asking is denied automatically. Only what's already approved in the rules or on the command line runs. It's the mode for scripts and pipelines, where there's nobody to answer.

Example · review in a pipeline
claude -p "Review the diff against main and list risks" \
  --permission-mode dontAsk \
  --allowedTools "Read,Grep,Bash(git diff *)"

Here Claude can read, search and see the diff. If it tries anything else, it's denied and it carries on with what it has.

bypassPermissions: never asks

Claude does everything without asking. It's the same as starting with claude --dangerously-skip-permissions.

Only use it inside a disposable container or VM, with no real credentials or production access, for example a devcontainer for an experiment.

Don't use it on your work machine. One wrong command can delete files or publish something. Admins usually block it in managed settings (session 6).

Which mode should I use?

  • I'm new to this repodefault or plan
  • Change across several files, or an ambiguous taskplan, then acceptEdits once approved
  • Bug with a clear repro in a single filedefault or straight to acceptEdits
  • Long, repetitive refactor on a branchauto
  • Script or CI pipelinedontAsk with --allowedTools
  • Disposable container for experimentsbypassPermissions

Slash commands

Type / at the start of the prompt and a menu appears with every command and a short description; keep typing to filter. Many accept text after the name. Your team's skills show up in this menu too (session 5).

You don't need to learn them all. These are the ones used in a normal task, grouped by when you need them.

Before you start

  • /initAnalyzes the repo and generates an initial CLAUDE.md. Used once per repo (session 4).
  • /modelOpens the model picker; ← → adjust effort. Directly: /model sonnet.
  • /effortChanges only the effort: /effort low for something mechanical, /effort xhigh for a hard bug.
  • /planEnters Plan mode with the task: /plan add pagination to the refunds endpoint.
  • /add-dirGives access to another folder: /add-dir ../shared-contracts if the task touches another repo.

While you work: looking after context

Context is everything Claude has in its head: your conversation, the files it read, command output. When it fills up or gets mixed with old topics, answers get worse. One long session with mixed topics performs worse than two focused sessions.

  • /contextShows what's taking up context: CLAUDE.md, MCP tools, files, history. Look here if Claude starts forgetting things.
  • /compactSummarizes the conversation to free space and keep going on the same task. You can guide it: /compact keep the API decisions and the pending tests.
  • /clearClears the conversation and starts fresh. Use it between unrelated tasks.
  • /btwA side question that doesn't stay in the history: /btw which EF Core version does this repo use?
  • /rewindTakes code and conversation back to an earlier point. Shortcut: Esc Esc. Use it when Claude went down the wrong path.
  • /branchCreates a branch of the conversation to try another idea without losing the current one.
  • /permissionsView and edit the allow / ask / deny rules without opening the file.

When you finish

  • /diffShows every change in the session. Read it as if someone else wrote it.
  • /code-reviewA second review of the change: bugs, edge cases, code that can be simplified.
  • /security-reviewA security-focused review. Use it if you touched authentication, payments or personal data.
  • /usageThe session's tokens and cost. Useful for calibrating model and effort.

Sessions

  • /renameNames the session: /rename PAY-482-refund-discount. That way you'll find it tomorrow.
  • /resumeOpens the list of previous sessions to pick one up.
  • /exportSaves the conversation to a text file, for example to document a decision.

Configuration and diagnostics

  • /configAll settings in one panel.
  • /memoryEdits CLAUDE.md and auto memory (session 4).
  • /statusCurrent model, account, version and permission mode.
  • /doctorDiagnoses installation or configuration problems. First step when something isn't working.

No slash, just as useful

  • Shift+TabCycles through permission modes.
  • EscInterrupts Claude without losing its progress. Then you type the correction.
  • Esc EscOpens rewind (same as /rewind).
  • @Mentions a file with autocomplete: @src/Payments/RefundService.cs.
  • !Runs a shell command and Claude sees the output: !git status.
  • Ctrl+GOpens your editor to write a long prompt calmly.
  • Ctrl+RSearches the prompts you typed before.

Practice

Lab 3 · First feature with Claude Code

60 min
  1. In the practice repo, open claude and ask: "Explain this repo's architecture and how I run the build and tests."
  2. Turn on Plan mode and ask for a small feature. Example: "Add GET /orders/{id}/refunds with pagination, validation and integration tests using WebApplicationFactory." "Add GET /orders/:id/refunds in NestJS with pagination, a DTO validated with class-validator and tests with Vitest + Supertest."
  3. Correct at least one point of the plan before approving it.
  4. Switch to acceptEdits and let it implement. Watch how it runs dotnet testpnpm test and fixes failures.
  5. Review with /diff, run /code-review and ask for the commit.
  6. Check /usage to see what the task cost.
