MCP in Claude Code

Terminal
# Remote server (HTTP) shared with the team via .mcp.json
claude mcp add --transport http --scope project notion https://mcp.notion.com/mcp
# (authenticates with OAuth from /mcp; if the server uses a token, put it in .mcp.json with ${VAR}, see below)

# Local server (stdio); everything after -- is passed to the server
claude mcp add --transport stdio --env DB_URL=postgres://localhost/dev db -- npx -y <postgres-mcp-package>

claude mcp list          # status of all of them
claude mcp remove db
ScopeWhere it's storedShared
local (default)~/.claude.json, this project onlyNo
project.mcp.json at the repo rootYes, through git

.mcp.json
{
  "mcpServers": {
    "internal-docs": {
      "type": "http",
      "url": "${DOCS_MCP_URL:-https://mcp.internal.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_MCP_TOKEN}" }
    }
  }
}
  • ${VAR} and ${VAR:-value} expand from the environment: secrets never go in the file.
  • Servers in .mcp.json ask for approval the first time you open the repo.
  • claude.ai connectors (the ones the admin enabled) show up automatically in Claude Code if you sign in with claude.ai. /mcp lists them and lets you authenticate.
  • Every MCP server adds tools to the context. Connect the ones the team uses, not every one that exists.
Azure stack: for .NET teams an Azure DevOps or Azure MCP server is usually worth it (work items, pipelines, resources). Make sure it comes from a trusted source and give it minimal permissions.

Connectors in claude.ai

  • The admin enables each connector and can set its actions to read-only, approval-required or blocked.
  • Custom connectors (remote MCP servers): only Owners can add them on Team/Enterprise. The connection comes from Anthropic's cloud, so the server must be reachable from the internet or allowlist Anthropic's IPs.
  • With organization-wide authorization (Okta), the admin authorizes once and members inherit access.

Plugins: distributing the team's configuration

A plugin bundles skills, subagents, hooks and MCP servers so they install with one command. A marketplace is a repo with a catalog of plugins. That way the session 5 configuration reaches every repo without copying files.

Plugin structure
platform-tools/
├── .claude-plugin/plugin.json   # { "name", "description", "version" }
├── skills/new-migration/SKILL.md
├── agents/security-reviewer.md
├── hooks/hooks.json
└── .mcp.json
.claude-plugin/marketplace.json (marketplace repo)
{
  "name": "company-tools",
  "owner": { "name": "Platform Team" },
  "plugins": [
    { "name": "platform-tools", "source": "./plugins/platform-tools",
      "description": "The team's skills, hooks and agents" }
  ]
}
Each repo's .claude/settings.json
{
  "extraKnownMarketplaces": {
    "company-tools": { "source": { "source": "github", "repo": "my-org/claude-plugins" } }
  },
  "enabledPlugins": { "platform-tools@company-tools": true }
}

Manually: /plugin marketplace add my-org/claude-plugins and /plugin install platform-tools@company-tools. The plugin's skills are invoked as /platform-tools:new-migration. If the marketplace repo is private, each developer needs read access to it on GitHub.

GitHub: @claude in issues and PRs

The quick way is /install-github-app inside Claude Code (requires an authenticated gh and repo admin rights): it installs the GitHub App, creates the secret and opens a PR with the workflow. After that, anyone with write access types @claude in an issue or PR.

.github/workflows/claude.yml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 15"
  • With a subscription instead of an API key: claude setup-token generates a token; use it as claude_code_oauth_token. For the whole organization, a Console API key or OIDC federation is better (the token is tied to whoever generated it).
  • With prompt: the action runs without a mention (on every PR, on a cron). It can invoke the repo's skills: prompt: "/skill-name".
  • If you use Azure DevOps or GitLab, run Claude Code in headless mode inside the pipeline (below).

Governance: managed settings

Managed settings have the highest priority: no user or repo can override them. They're deployed via MDM, a system file or the admin console. There's also a policy CLAUDE.md in /Library/Application Support/ClaudeCode/ (macOS), /etc/claude-code/ (Linux/WSL) or C:\Program Files\ClaudeCode\ (Windows).

managed-settings.json (example)
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(//**/.env)",
      "Read(~/.ssh/**)",
      "Read(~/.azure/**)",
      "Bash(az keyvault secret show *)"
    ]
  },
  "forceLoginMethod": "claudeai"
}
  • allowManagedPermissionRulesOnly makes only the admin's rules count.
  • forceLoginOrgUUID forces use of the organization account.
  • Skills, subagents and hooks from managed settings take priority over user and repo ones.
