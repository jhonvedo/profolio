A single real flow that uses almost everything covered in the program. You take a GitHub issue and type one command: /resolve-issue 1. In about 25 minutes the team watches Claude read the issue over MCP, explore with a subagent, plan with a strong model, implement, run into a security hook, delegate tests and review to subagents on other models, and open the PR. At the end, an @claude comment on the PR triggers the GitHub Action.

Preparation (the day before)

Issue #1

GitHub · Issue #1
Title: Endpoint to list an order's refunds

As a support agent I want to see an order's refunds so I can answer complaints.

Acceptance criteria
- GET /orders/{id}/refunds returns the paginated list (page, pageSize; pageSize max 50).
- 404 if the order doesn't exist.
- Only users with the "Support" policy.
- Sorted from most recent to oldest.
- Raise the payments client HTTP timeout to 30 s in appsettings.Production.json.

.claude/skills/resolve-issue/SKILL.md
---
description: Resolves a GitHub issue end to end (read, plan, implement, test, review, open PR). Only when the user runs /resolve-issue.
argument-hint: "[issue-number]"
arguments: [issue]
disable-model-invocation: true
allowed-tools: mcp__github Bash(git checkout -b *) Bash(git add *) Bash(git commit *) Bash(dotnet build *) Bash(dotnet test *)Bash(pnpm -r test) Bash(pnpm -r typecheck)
---
# Resolve issue #$issue

## Repo state
!`git status --short`
!`git log --oneline -3`

## Process
1. Read. Using the `github` MCP server's tools, read issue #$issue in this
   repository and its comments. Summarize the requirement and list the acceptance criteria.
2. Explore. Delegate the search for relevant files to the Explore subagent.
   Ask only for paths and a short summary.
3. Plan. Present a numbered plan: files to touch, tests, risks.
   If a criterion touches protected or production files, say so in the plan.
   WAIT for the user's approval.
4. Branch. `git checkout -b issue-$issue` plus a short descriptive suffix.
5. Implement following CLAUDE.md and `.claude/rules/`.
6. Tests. Delegate one test per acceptance criterion to the `test-writer` subagent.
   Then run the full suite.
7. Review. Delegate to the `security-reviewer` subagent. Fix high-severity findings.
8. Publish. Conventional commit mentioning #$issue, `git push -u origin HEAD`
   and create the PR with the `github` MCP tools. PR body:
   summary, how it was tested, review findings, follow-ups for humans and `Closes #$issue`.
9. Finish with the PR link and a table: criterion → status.

The whole skill is in English: the description loads on every turn, and the body only when invoked. git push is left out of allowed-tools on purpose: since it's set to ask in settings.json, Claude will have to ask for permission live.

You are a testing specialist for ASP.NET Core.
- Integration tests with WebApplicationFactory and FluentAssertions; follow the existing ones in tests/.
- One test per acceptance criterion, named Method_Scenario_Result.
- Cover the edge cases: 404, 403 without the policy, pageSize > 50, empty list.
- Run `dotnet test` and report: tests created, result, criteria coverage.
- Don't modify production code; if a test reveals a bug, report it.

Plan B

  • The GitHub MCP won't authenticateCheck GITHUB_PAT and /mcp reconnect. If it still fails, ask Claude to use gh issue view 1 and gh pr create. Explain that the result is the same with a different integration.
  • The model is slow or you hit a usage limitclaude -r "demo-rehearsal" --fork-session and walk through the session you already did. It also shows how work gets resumed.
  • Claude doesn't touch the production fileAsk directly: "also apply the timeout change". The block shows up the same way.
  • Tests take too longBefore the demo, put the command that runs only the affected test project in CLAUDE.md.
  • The GitHub Action is slowShow the rehearsal PR where it already ran and come back at the end of the session.
  • The network goes downRecord the second rehearsal on video and have it ready.
