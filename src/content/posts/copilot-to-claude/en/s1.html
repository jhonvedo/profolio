Companion course: Claude 101

Models and effort

  • Claude Fable 5.1The most capable for code and knowledge work (September 2026). Large refactors, architecture design, hard bugs.
  • Claude Opus 5Complex multi-step tasks with a good balance of speed. Has Fast mode.
  • Claude Sonnet 5Daily work: medium features, tests, explaining code. Fast and economical.
  • Claude Haiku 4.5Short, high-volume tasks; a good fit for search subagents.

Concrete examples by task type in Concepts → Model and effort. Effort (Low, Medium, High, Extra High, Max) controls how much the model reasons before answering. More effort is better for ambiguous problems and worse for simple questions, because it takes longer and uses more quota. On Fable 5.1 and Opus 5, reasoning ("Thinking") is always on.

Projects: the team's shared knowledge

A Project groups chats that share three things: knowledge files, instructions and their own memory. It's the place for what doesn't live in the repository: ADRs, API standards, style guides, business documentation, OpenAPI contracts.

  • Capacity: when knowledge approaches the context limit, Claude automatically switches to RAG and searches the files instead of loading them all (up to ~10× more capacity). 30 MB limit per file.
  • Sharing (Team/Enterprise): "Can view" or "Can edit", with people, groups or the whole organization. They show up under "Shared with me".
  • Instructions: write them as you would for a new teammate: stack, conventions, what to avoid, answer format.
Sample instructions · "Payments Platform" Project
You are part of the Payments Platform team.
Stack: .NET 8 (ASP.NET Core Minimal APIs, EF Core, SQL Server, Azure)Node 22 + TypeScript (NestJS, Prisma, PostgreSQL, Next.js).
- Answer in English; code and code comments in English.
- Follow the ADRs in the knowledge folder; if a proposal contradicts an ADR, say so.
- Before proposing code, ask if business information is missing.
- Prefer examples with tests. Flag any assumption explicitly.

Memory and past chats

Memory keeps durable facts (role, preferences, decisions) as editable topics. Each Project has its own separate memory. Past-chat search lets you ask "what did we decide about API versioning?". You can pause it, reset it or use incognito chats.

Team rule. Personal memory doesn't replace documentation. If a decision affects everyone, it goes into an ADR in the repo or into the Project's knowledge, not into one person's memory.

Artifacts, Docs and Slides

Artifacts

Pages, diagrams, SVGs and React apps that Claude publishes with their own link. They can call Claude and connectors (each visitor uses their own quota).

Claude Docs

Living documents with co-editing, comments and @Claude in the thread. Export to .docx, PDF, .md or Google Docs. Ideal for specs and postmortems.

Claude Slides

16:9 presentations exportable to PPTX or PDF. For sprint demos and technical proposals.

Research, files and connectors

  • Research ("+" → Research): several chained searches with citations. Useful for comparing libraries or evaluating a migration. Requires web search to be on.
  • File creation: Claude creates and edits .xlsx, .pptx, .docx and PDF by running code in a sandbox. The admin controls that sandbox's internet egress.
  • Connectors: GitHub, Jira/Confluence, Linear, Slack, Google Drive, Notion, Figma. They inherit the user's permissions in the source system: Claude can't see anything you can't.
  • Organization skills: an admin uploads a .zip with a SKILL.md in Organization settings → Skills and it becomes available to everyone (session S5).

Data and privacy on commercial plans

The essentials: Team and Enterprise conversations are not used to train models by default. The exception is thumbs up/down feedback, which retains that conversation; the admin can turn it off with the "Rate chats" setting. Enterprise adds custom retention, audit logs, SCIM and customer-managed keys.

Practice

Lab 1 · The team Project

45 min
  1. Create a Project named after the product. Upload 3–5 real documents: an ADR, the API standard, a service's OpenAPI contract and the style guide.
  2. Write instructions based on the template above and adapt them to your team.
  3. Ask: "According to our ADRs, how should we expose a refunds endpoint?". Check whether it cites the right documents.
  4. Switch to Sonnet 5 on low effort and repeat. Compare quality and time with Fable 5.1 on high effort.
  5. Ask for a Claude Doc with the endpoint design and leave an @Claude comment asking it to add the error cases.
  6. Share the Project with the team as "Can view".
