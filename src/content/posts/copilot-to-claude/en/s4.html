The .claude folder

Recommended repo structure
my-repo/
├── CLAUDE.md                 # team instructions (committed)
├── CLAUDE.local.md           # personal (gitignored)
├── .mcp.json                 # team MCP servers (committed)
└── .claude/
    ├── settings.json         # permissions, hooks, env, model (committed)
    ├── settings.local.json   # personal overrides (gitignored)
    ├── rules/                # path-scoped rules
    │   ├── api.md
    │   └── testing.md
    ├── skills/               # /commands and procedures
    │   └── new-migration/SKILL.md
    ├── agents/               # subagents
    │   └── security-reviewer.md
    └── hooks/                # scripts called by hooks
        ├── protect-files.sh
        └── format.sh

On your machine, ~/.claude/ has the same structure for personal things (settings, CLAUDE.md, rules, skills, agents), plus per-project auto memory and history.

A CLAUDE.md that works

  • Under 200 lines. Long files eat context and lower adherence. Move the detail into path-scoped rules.
  • What Claude can't figure out on its own: exact commands, decisions and their why, known pitfalls. Don't copy what the code already says.
  • Concrete and verifiable: "Use Result<T> for business errors" beats "handle errors properly".
  • No contradictions: if two rules clash, Claude picks one at random.
  • Start with /init: it analyzes the repo and generates a draft. If .github/copilot-instructions.md already exists, it reads it and pulls in what's relevant.
CLAUDE.md · .NET API
# Orders API

## Stack
- .NET 8, ASP.NET Core Minimal APIs, EF Core 8 (SQL Server), MediatR
- Tests: xUnit + FluentAssertions + Testcontainers

## Commands
- Build: `dotnet build Orders.sln`
- Tests: `dotnet test Orders.sln --no-build`
- Format: `dotnet format Orders.sln --verify-no-changes`
- New migration: `dotnet ef migrations add <Name> -p src/Orders.Infrastructure -s src/Orders.Api`

## Architecture
- Clean Architecture: Api → Application → Domain. Infrastructure implements Application interfaces.
- Domain doesn't reference EF Core or ASP.NET Core.

## Conventions
- Async end to end; propagate `CancellationToken`.
- Business errors with `Result<T>`; exceptions only for the unexpected.
- Never edit a migration that's already applied: create a new one.
- Sensitive configuration only via User Secrets or Key Vault; never in appsettings.

## Before finishing a task
- Run build, tests and format. If something fails, fix it before reporting.

Importing other files

@path/file inside a CLAUDE.md loads that file at startup (paths relative to the importing file, up to 4 levels of nesting). To mention a path without importing it, wrap it in backticks. Imports outside the repo ask for approval the first time.

How they load

Claude Code loads CLAUDE.md and CLAUDE.local.md from the current directory and every parent; they're concatenated, not overridden. Ones in subdirectories load when Claude reads files there. In monorepos, claudeMdExcludes avoids loading other teams' files. If the repo only has AGENTS.md, Claude reads it as the project instructions.

Path-scoped rules

They're the equivalent of Copilot's *.instructions.md with applyTo. They only load when Claude reads matching files, so they don't spend context the rest of the time.

.claude/rules/endpoints.md
---
paths:
  - "src/Orders.Api/Endpoints/**/*.cs"
---
# Endpoint rules
- Each endpoint in its own static class with `MapXxx(this IEndpointRouteBuilder)`.
- Validate with FluentValidation; return errors with `Results.ValidationProblem`.
- Return `TypedResults` so OpenAPI documents the responses.
- Explicit authorization: `.RequireAuthorization("policy")`.
.claude/rules/testing.md
---
paths:
  - "**/*.{spec,test}.ts"
  - "apps/web/e2e/**/*.ts"
---
# Test rules
- One `describe` per unit; names in the form "should … when …".
- No `setTimeout` in tests: use Vitest fake timers.
- In e2e, select by role or `data-testid`, never by CSS classes.
- Mock only at the edges (HTTP, DB); don't mock your own code.

Auto memory

Claude keeps its own notes while it works: your preferences, corrections you give it, project decisions and where to find things outside the repo. They live in ~/.claude/projects/<project>/memory/ and load at startup (first 200 lines). Manage them with /memory, which also opens the CLAUDE.md files for editing. Turn it off with "autoMemoryEnabled": false.

Team rule. If you correct Claude on something twice, don't rely on auto memory: add it to CLAUDE.md or a rule so the whole team has it.

settings.json: layers and permissions

Precedence order, highest to lowest: managed settings (organization) → CLI flags → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json.

How permissions are evaluated: first deny, then ask, then allow. The first match wins, and a deny in any layer can't be overridden by an allow.
.claude/settings.json · .NET
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(dotnet build *)",
      "Bash(dotnet test *)",
      "Bash(dotnet format *)",
      "Bash(dotnet ef migrations add *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(dotnet ef database update *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(**/appsettings.Production.json)",
      "Read(~/.microsoft/usersecrets/**)",
      "Bash(dotnet nuget push *)"
    ]
  },
  "env": { "DOTNET_CLI_TELEMETRY_OPTOUT": "1" }
}
.claude/settings.json · Node
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(pnpm test *)",
      "Bash(pnpm lint *)",
      "Bash(pnpm -r typecheck)",
      "Bash(pnpm --filter api test *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(pnpm add *)",
      "Bash(pnpm --filter api prisma migrate *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(**/secrets/**)",
      "Bash(npm publish *)",
      "Bash(pnpm publish *)"
    ]
  }
}

Rule syntax

  • Bash(git log *): the * goes after the subcommand. Bash(git *) would allow all of git, including push.
  • Read/Edit use gitignore-style patterns: ./path relative to the current directory, /path relative to the settings file, ~/path from your home, //path absolute.
  • WebFetch(domain:learn.microsoft.com), mcp__github__create_issue, Agent(name).
  • Bash rules that try to restrict arguments are fragile (curl with different options). For real guarantees use hooks or the sandbox.
  • /permissions shows and edits them; /fewer-permission-prompts analyzes your sessions and suggests an allowlist.

settings.json recipes

So far we've covered permissions. But settings.json does much more: notifications, status line, default model, environment variables, how you authenticate. These recipes are the most useful day to day.

Almost all of them are personal: they go in ~/.claude/settings.json (your user folder) and apply to all your repos. When a recipe makes sense for the whole team, I say so.

Get notified when Claude finishes or needs permission

The problem: you give Claude a task, switch windows, and don't notice it's been waiting five minutes for your approval. The fix is two hooks:

  • Notification fires when Claude needs your attention: a pending permission or a long wait.
  • Stop fires every time Claude finishes responding.
~/.claude/settings.json · Windows (sound, nothing to install)
{
  "hooks": {
    "Notification": [
      { "matcher": "permission_prompt|idle_prompt",
        "hooks": [{ "type": "command",
          "command": "powershell.exe -NoProfile -Command \"[System.Media.SystemSounds]::Exclamation.Play()\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
          "command": "powershell.exe -NoProfile -Command \"[System.Media.SystemSounds]::Asterisk.Play()\"" }] }
    ]
  }
}

Two different sounds: one when it's waiting for permission and another when it's done. That way you know without looking whether you need to go back.

Windows with a visual notification (BurntToast module)
# Once, in PowerShell:
Install-Module BurntToast -Scope CurrentUser

# Then, in the settings.json hook:
"command": "powershell.exe -NoProfile -Command \"New-BurntToastNotification -Text 'Claude Code','Needs your attention'\""
macOS and Linux: the hook's "command" line
// macOS
"command": "osascript -e 'display notification \"Needs your attention\" with title \"Claude Code\" sound name \"Glass\"'"

// Linux
"command": "notify-send 'Claude Code' 'Needs your attention'"
It goes in your personal configuration, not in the repo. The command depends on the operating system and everyone prefers different notifications. To test it, ask Claude for something that needs permission and switch windows.

Status line

A line below the prompt that always shows what matters: model, folder, branch and how much context you're using. Claude Code runs your script whenever something changes and passes it the session data as JSON.

The quick way is to ask Claude for it: /statusline show model, git branch and context %. It generates the script and registers it. If you'd rather do it by hand:

~/.claude/statusline.sh
#!/usr/bin/env bash
# Claude Code sends the session data on stdin, as JSON.
INPUT=$(cat)
MODEL=$(echo "$INPUT" | jq -r '.model.display_name')
DIR=$(echo "$INPUT" | jq -r '.workspace.current_dir' | xargs basename)
CTX=$(echo "$INPUT" | jq -r '.context_window.used_percentage // 0')
BRANCH=$(git -C "$(echo "$INPUT" | jq -r '.workspace.current_dir')" branch --show-current 2>/dev/null)

echo "[$MODEL] $DIR ${BRANCH:+on $BRANCH} · ${CTX}% context"
~/.claude/settings.json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/statusline.sh"
  }
}

Result: [Sonnet 5] orders-api on PAY-482 · 34% context. Once the percentage goes past 70–80%, it's a good time for /compact or /clear. Requires jq.

Use an API key instead of the subscription

By default Claude Code uses your claude.ai account and consumes the plan's quota. You can use a Claude Console API key instead, billed per token. It makes sense for CI pipelines, scripts, or if your company bills usage through the API.

Option 1 · environment variable
# PowerShell (this terminal only)
$env:ANTHROPIC_API_KEY = "sk-ant-..."

# bash / zsh
export ANTHROPIC_API_KEY="sk-ant-..."

claude   # uses the API key instead of the account
Option 2 · apiKeyHelper in ~/.claude/settings.json
{
  // A script that prints the key. That way it isn't written in any file.
  "apiKeyHelper": "~/.claude/get-api-key.sh"
}

The script can read the key from your password manager or a company vault. It's the safest option and the right one for teams.

If the company uses Amazon Bedrock or Google Vertex
# Bedrock: uses your AWS credentials
export CLAUDE_CODE_USE_BEDROCK=1
export AWS_REGION=us-east-1

# Vertex AI: uses your Google Cloud credentials
export CLAUDE_CODE_USE_VERTEX=1
export CLOUD_ML_REGION=us-east5
export ANTHROPIC_VERTEX_PROJECT_ID=my-project
Never put an API key in the repo's .claude/settings.json or in any file that goes into git. If the admin set forceLoginMethod in managed settings, the API key may not be allowed: check first.

Default model, environment and folders

The repo's .claude/settings.json (works for the whole team)
{
  // Model each session in this repo starts with
  "model": "sonnet",

  "permissions": {
    // Always start in Plan mode
    "defaultMode": "plan",
    // Folders outside the repo Claude can access
    "additionalDirectories": ["../shared-contracts"]
  },

  // Environment variables for every command Claude runs
  "env": {
    "ASPNETCORE_ENVIRONMENT": "Development",
    "DOTNET_CLI_TELEMETRY_OPTOUT": "1""NODE_ENV": "development",
    "NEXT_TELEMETRY_DISABLED": "1"
  }
}

The // comments are for explanation; delete them in the real file. For the subagents' model, add "CLAUDE_CODE_SUBAGENT_MODEL": "haiku" inside env.

Useful switches

  • "disableAllHooks": trueTemporarily turns off every hook. Handy if a hook fails and blocks you.
  • "autoMemoryEnabled": falseTurns off auto memory if you'd rather everything live in CLAUDE.md.
  • "claudeMdExcludes"In monorepos, avoids loading other teams' CLAUDE.md files.

Your personal settings.json, all together

~/.claude/settings.json · full example (Windows)
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "statusLine": { "type": "command", "command": "bash ~/.claude/statusline.sh" },
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff *)", "Bash(git log *)"],
    "deny": ["Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(~/.azure/**)"]
  },
  "hooks": {
    "Notification": [
      { "matcher": "permission_prompt|idle_prompt",
        "hooks": [{ "type": "command",
          "command": "powershell.exe -NoProfile -Command \"[System.Media.SystemSounds]::Exclamation.Play()\"" }] }

The $schema makes VS Code and Rider autocomplete the keys and flag errors as you edit. After changing the file, open a new session or check with /hooks and /status that it loaded.

Practice

Lab 4 · Set up the team repo

60 min
  1. If the repo has .github/copilot-instructions.md, run /init and check what it pulled in. If not, run /init anyway.
  2. Trim CLAUDE.md to under 200 lines. Move endpoint- and test-specific content to .claude/rules/.
  3. Create .claude/settings.json with the allow/ask/deny from the example, adapted to your commands.
  4. Create your CLAUDE.local.md and add it to .gitignore along with .claude/settings.local.json.
  5. Open a new session and run /context: check that the right files load.
  6. Ask Claude to read .env: it should refuse because of the deny.
  7. Open a PR with the .claude/ folder for the team to review.
