The commands that separate someone who "uses Claude" from someone who handles it fluently: naming and resuming sessions, working in parallel, turning plugins on and off, controlling costs and keeping everything up to date.

A recommended work routine

A normal day with Claude Code
# 1. Start with a name: you'll find it easily later
claude -n "PAY-482-partial-refund"

# 2. Inside the session
/model            # model and effort suited to the task
/plan …           # plan before touching code
/context          # check how much context you're using
/diff             # review changes
/code-review      # a second look
/usage            # what it cost

# 3. The next day, pick up where you left off
claude -r "PAY-482-partial-refund"

Working in parallel

  • claude --bg "investigate the flaky payments test"Launches a background session and gives you your terminal back.
  • /background [prompt]Sends the current session to the background.
  • /fork [prompt]Copies the conversation into a new background session.
  • /tasks · /list-agentsSee background work, subagents and other sessions.
  • isolation: worktree (subagents)The subagent works in an isolated git worktree so it doesn't step on your files.
  • /desktop · /mobileContinue the session in the desktop app · QR code for the mobile app.
  • claude.ai/codeCloud sessions on GitHub; several at once from the browser or your phone.
Parallel without conflicts: two sessions editing the same folder step on each other: one undoes or breaks what the other does. For real parallel work, each session needs its own copy of the files: a git worktree.

Example: a feature and a bug at the same time

A worktree is another folder with its own branch, sharing the same git history. Claude Code creates them for you with -w: you're building the refund summary and an urgent bug comes in.

Two terminals, two tasks, zero collisions
# Once per repo: keep worktrees from showing up as untracked files
echo ".claude/worktrees/" >> .gitignore

# Terminal 1 · the feature
claude -w pay-12-summary
# → creates .claude/worktrees/pay-12-summary on branch worktree-pay-12-summary
> Implement GET /orders/{id}/refund-summary with its tests.

# Terminal 2 · the bug, without touching terminal 1's files
claude -w bug-7-balance
> Reproduce with a test that you can refund more than the order's balance, and fix it.

# Any terminal · what's running in parallel
git worktree list
  • On exitIf the worktree has changes or commits, Claude asks whether to keep or remove it. If you keep it, on exit it prints the command to come back: claude --worktree pay-12-summary --resume.
  • Where it starts fromBy default, from the remote's main branch (origin/main): every task starts clean. With "worktree": { "baseRef": "head" } in settings it starts from your current local branch.
  • A PR or an existing branchclaude -w "#123" fetches that PR from origin. For an existing branch or a folder outside the repo, by hand: git worktree add ../orders-hotfix hotfix/timeout, then cd ../orders-hotfix and claude; when done, git worktree remove ../orders-hotfix.
  • Parallel subagentsWith isolation: worktree in its frontmatter, each subagent edits in its own temporary worktree, removed automatically if it finishes without changes.

Sessions that talk to each other

Each session has its own context: what the bug session knows, the feature session doesn't. Instead of copying and pasting between terminals, one session can message another one that's open on your machine. They just need a name (/rename or -n), and you mention them with @, which autocompletes.

The example's two terminals, coordinating
# Terminal 2 · the bug is fixed
> /rename BUG-7-balance
> Explain to @PAY-12-summary what changed in CreateRefund and why.

# Terminal 1 · the feature, which depends on that calculation
> /rename PAY-12-summary
> /list-agents
# → the open sessions this one can reach
> Ask @BUG-7-balance how it now calculates the available balance and use the same in availableToRefund.
> Let me know when @BUG-7-balance finishes.
  • What travelsA text message written by Claude. The other session's history and files don't travel: that's what git is for.
  • When it arrivesBetween one tool call and the next if the session is working, or as a new turn if it's waiting.
  • What it can't doApprove permissions or change the receiving session's configuration.
  • RequirementsSessions open on the same machine (on Windows, v2.1.234 or later). A WSL session and a Windows session can't see each other.
  • If the session already endedThere's no one to ask. Resume it with claude -r BUG-7-balance, or leave its result in a file: /export bug-7.txt and in the other session According to @bug-7.txt, why do we validate in the endpoint?

Start from a session without touching it: --fork-session

Sometimes the valuable session is the research one: it already read the module, understood the rules and answered your questions. claude -r name resumes it and adds everything you do next. With --fork-session you resume it in a new copy: the original stays intact so you can start from it again as many times as you want.

One investigation, two tasks that start from it
# Monday · the session that understands the module
claude -n REF-analysis
> Explain the refund flow to me: endpoints, store, validations and tests. Don't change anything.

# Tuesday · the feature starts from that analysis, in a copy
claude -r REF-analysis --fork-session
> /rename PAY-12-summary
> With what you already know about the flow, plan GET /orders/{id}/refund-summary.

# Wednesday · the bug starts from the same analysis, without Tuesday's conversation
claude -r REF-analysis --fork-session
> /rename BUG-7-balance
> With what you already know about the flow, reproduce with a test the refund that exceeds the balance.
  • It copies the conversation, not the filesJust like /branch. If the copy and the original will edit at the same time, each one needs its own worktree.
  • It isn't freeThe copy starts with all of the original's context. Worth it if that analysis took a lot; if the research was short, a new session is cheaper.
  • Inside a session/branch forks right here to try another direction; /fork sends the copy to the background and you keep working in the original.

Good practices for working in parallel

  • One task, one worktree, one branch, one PR. Name the worktree after the ticket (-w pay-12-summary): that way you know what each folder, terminal and branch is.
  • Parallelize what's independent. Two tasks that touch the same files still collide when you integrate, just later. If they share a module, do them in sequence.
  • Set up each worktree's environment. It's a clean checkout: dependencies need installing (dotnet restore, pnpm install) and ignored files are missing. A .worktreeinclude at the root, in .gitignore syntax (for example .env), copies them into every new worktree automatically.
  • Mind what's shared outside git. If two sessions start the API or use the same local database, they collide: use another port or another database per worktree.
  • Few sessions at a time. Two or three you can actually review. Each session has its own context and uses its own quota (see Consumption and efficiency).
  • Review each branch separately. /diff and /code-review inside each worktree, green tests and one PR per branch. Parallelizing the work isn't parallelizing the review.
  • Watch your hooks. If Claude enters a worktree mid-session, $CLAUDE_PROJECT_DIR still points at the main checkout. A hook that needs the worktree's path should read the cwd field from its input.
  • Coordinate with messages, document in files. Messages between sessions work while both are open. What matters later (a decision, why something changed) goes in the repo: any session and any person can read docs/decisions/bug-7.md.
  • Clean up when done. git worktree list shows what's left; remove what's already merged with git worktree remove.

Plugins: install, enable, disable

Inside Claude Code
/plugin                                         # panel: Discover · Installed · Marketplaces · Errors · Stats
/plugin install csharp-lsp@claude-plugins-official
/plugin list --enabled                          # or --disabled
/plugin disable csharp-lsp@claude-plugins-official
/plugin enable  csharp-lsp@claude-plugins-official
/plugin uninstall csharp-lsp@claude-plugins-official
/reload-plugins                                 # applies changes made outside the panel

/plugin marketplace add my-org/claude-plugins
/plugin marketplace update company-tools
/plugin marketplace list
From the shell (scripts, onboarding)
claude plugin install platform-tools@company-tools --scope project
claude plugin uninstall platform-tools@company-tools --scope project
claude plugin details platform-tools@company-tools   # which skills, agents, hooks and MCP it ships
  • Scopes: user (you, all repos), project (the whole team, written to .claude/settings.json), local (you, this repo only). Managed-scope plugins are set by the admin and can't be removed.
  • If you uninstall a plugin the project enables, Claude Code asks whether to disable it just for you (override in settings.local.json) or for everyone.
  • The Installed tab flags plugins as "Not used recently": disable them: their skills, subagents and MCP servers take up context even when you don't use them.
  • The panel shows a plugin's context cost before you install it.
  • Useful plugins from the official marketplace: csharp-lsp and typescript-lsp (Claude sees compile errors while editing; they require installing csharp-ls or typescript-language-server), github, atlassian, commit-commands, pr-review-toolkit, security-guidance.

  • MCP/mcp status and OAuth · /mcp disable name / enable / reconnect · claude mcp list, get, remove
  • Hooks/hooks see configured ones · "disableAllHooks": true temporarily disable all · claude --debug see runs
  • Permissions/permissions · /fewer-permission-prompts suggests an allowlist based on your sessions
  • Memory/memory edits CLAUDE.md and auto memory

To understand what uses tokens and how to save without losing quality, see Consumption and efficiency.

In claude.ai

  • Customize → Skills: turn skills on or off (organization skills come on; you can turn them off for yourself).
  • Customize → Connectors: connect accounts. In each chat, the tools menu lets you turn off connectors you don't need to save context.
  • Settings: pause or reset memory, incognito chats, default model and effort.
  • Projects: rename, archive and change sharing permissions.
  • Skills and plugins enabled in claude.ai sync to Claude Code. Synced plugins show up in /plugin → Installed with origin synced; you disable them there, unless the organization marks them as required.
