Skills and subagents are the two most confused pieces, because both are ways to give Claude work. The difference is who does it and with what context. This chapter expands on the table in Concepts; in session 5 you create them in the repo.

Companion courses: Introduction to Agent Skills · Introduction to Subagents

Skill vs. agent: the most confusing difference

Skill = "how it's done"

It's procedural knowledge. While unused, Claude only sees its name and description (a few lines). When invoked, its instructions enter the current conversation's context and the same Claude follows them. You see every step.

Examples: creating an EF Core migration, preparing a release, the changelog format, the checklist for a new endpoint.

Subagent = "who does it"

It's a separate worker. It starts with a clean context (it doesn't see your conversation), uses only the tools you allow and can use another model. It can read 40 files and return a 20-line summary: your main session doesn't fill up.

Examples: security reviewer, code researcher, test writer, log analyst.

How they combine

You don't have to pick one or the other. They work together in three ways.

1 · A skill that runs in a subagent. Normally a skill runs inside your conversation. With context: fork (details below), Claude Code creates a subagent, hands it the skill as its task, and only the summary comes back to your conversation; meanwhile you can keep working. agent: picks which subagent does the work (general-purpose if you don't set it).

.claude/skills/investigate/SKILL.md
---
description: Investigates how something works in this repo and returns a short summary with file paths. Use it for questions that require reading many files.
context: fork
agent: Explore
---
Investigate $ARGUMENTS in this repository: find the relevant files,
read them and return a short summary with paths and lines.

What is agent: Explore? It tells Claude Code which subagent runs the skill. Explore ships with Claude Code and is built for searching: it finds and reads files, but it can't edit them, and it starts with a minimal context (it doesn't load CLAUDE.md). It's the natural choice for a skill that only investigates. The alternatives:

  • agent: ExploreRead-only and fast. For investigating, searching or summarizing.
  • agent: PlanResearches to build a plan, without editing.
  • agent: general-purposeCan read, edit and run commands. It's the one used if you don't set agent:.
  • agent: security-reviewerAny custom subagent from .claude/agents/, with its own prompt, tools and model.
What using it looks like (illustrative)
> /investigate how a partial refund is calculated

# Claude Code creates an Explore subagent and hands it the skill with your argument.
# You keep working. The subagent, on its own:
#   searches "Refund" → 14 files · reads the service, the discount policy and the tests
# None of that enters your context. When it finishes, only this arrives:

A partial refund is calculated in RefundService.CalculateRefund
(src/Payments/RefundService.cs:88)RefundService.calculateRefund
(apps/api/src/refunds/refund.service.ts:88). It applies the order's discount
and rounds at the end. Tests cover fixed discounts but not percentage ones.

The subagent read fourteen files; your session only got four lines.

2 · A subagent that starts out knowing a skill. With skills: in the subagent's frontmatter, the full content of those skills goes into its context from the start, without it having to look them up. When Claude delegates to api-implementer, that subagent already knows the team's conventions from its first message.

.claude/agents/api-implementer.md
---
name: api-implementer
description: Implements API endpoints following the team's conventions.
skills: [api-conventions]
---
Implement the endpoint you're asked for, following the preloaded conventions.

3 · A skill that splits the work among subagents. Here the skill does not use context: fork: it runs in your session because it's the coordinator. At each step it asks a different subagent to do one part, and each one works in its own context and returns only its result. The skill gathers the answers and gives you the summary.

.claude/skills/review-branch/SKILL.md
---
description: Reviews the current branch before opening a PR (scope, tests, security). Only when the user runs /review-branch.
disable-model-invocation: true
---
Review the current branch before opening the PR:
1. Delegate to the Explore subagent: list the files changed against main
   and which modules they touch. Ask only for paths and one line per module.
2. Delegate to test-writer: check that every change has a test and write the missing ones.
3. Delegate to security-reviewer: review the diff and report findings with file and line.
4. With the three results, give me a table: module → tests → findings.

When you type /review-branch, your session sees three delegations and three summaries, not the files each subagent read. security-reviewer is the subagent from session 5; test-writer would be a similar one, allowed to edit test files.

What context: fork changes

It's a single line in the skill's frontmatter, but it changes where and how the skill runs:

Regular skillSkill with context: fork
Where it runsIn your conversation, with the same ClaudeIn a new subagent of the type set by agent: (general-purpose by default)
What it knowsEverything already discussed in the sessionOnly the skill's text and the arguments. It doesn't see your conversation
What you see while it worksEvery step, in your sessionNothing: it runs in the background and you keep working. With background: false, you wait for the result
What stays in your contextEverything it read and ranOnly the summary it returns
ModelThe session's, or model: while it answersmodel: sets the subagent's model
Mind the name. "Fork" sounds like copying the conversation, but it doesn't copy it: the subagent starts without knowing anything you discussed. That's why the skill has to carry everything it needs, and whatever changes between uses goes in the arguments ($ARGUMENTS). With agent: Explore, it doesn't even load CLAUDE.md.
  • Use it when…The skill reads a lot to return a little: investigating a flow, auditing dependencies, summarizing logs, reviewing a module.
  • Don't use it when…The skill depends on what you've already discussed, has to edit files while you watch, or will ask you questions along the way.
