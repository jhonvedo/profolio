Un solo flujo real que usa casi todo lo visto en el programa. Tomas un issue de GitHub y escribes un comando: /resolver-issue 1. En unos 25 minutos el equipo ve a Claude leer el issue por MCP, explorar con un subagente, planear con un modelo fuerte, implementar, chocar con un hook de seguridad, delegar tests y revisión a subagentes con otros modelos, y abrir el PR. Al final, un comentario @claude en el PR dispara la GitHub Action.

Preparación (el día anterior)

El issue #1

GitHub · Issue #1
Título: Endpoint para listar los reembolsos de un pedido

Como agente de soporte quiero ver los reembolsos de un pedido para responder reclamos.

Criterios de aceptación
- GET /orders/{id}/refunds devuelve la lista paginada (page, pageSize; pageSize máximo 50).
- 404 si el pedido no existe.
- Solo usuarios con la política "Support".
- Ordenados del más reciente al más antiguo.
- Subir el timeout HTTP del cliente de pagos a 30 s en appsettings.Production.json.
GitHub · Issue #1
Título: Endpoint para listar los reembolsos de un pedido

Como agente de soporte quiero ver los reembolsos de un pedido para responder reclamos.

Criterios de aceptación
- GET /orders/:id/refunds devuelve la lista paginada (page, pageSize; pageSize máximo 50).
- 404 si el pedido no existe.
- Solo usuarios con rol "support".
- Ordenados del más reciente al más antiguo.
- Subir PAYMENTS_TIMEOUT_MS a 30000 en .env.production.

El último criterio es la trampa intencional: toca un archivo de producción que la regla deny y el hook de protección bloquean. Así el equipo ve el control en acción sin forzarlo.

.claude/skills/resolver-issue/SKILL.md
---
description: Resolves a GitHub issue end to end (read, plan, implement, test, review, open PR). Only when the user runs /resolver-issue.
argument-hint: "[issue-number]"
arguments: [issue]
disable-model-invocation: true
allowed-tools: mcp__github Bash(git checkout -b *) Bash(git add *) Bash(git commit *) Bash(dotnet build *) Bash(dotnet test *)Bash(pnpm -r test) Bash(pnpm -r typecheck)
---
# Resolver el issue #$issue

## Estado del repo
!`git status --short`
!`git log --oneline -3`

## Proceso
1. Leer. Con las herramientas del servidor MCP `github`, lee el issue #$issue de este
   repositorio y sus comentarios. Resume el requisito y lista los criterios de aceptación.
2. Explorar. Delega al subagente Explore la búsqueda de los archivos relevantes.
   Pide solo rutas y un resumen corto.
3. Planear. Presenta un plan numerado: archivos a tocar, tests, riesgos.
   Si un criterio toca archivos protegidos o de producción, dilo en el plan.
   ESPERA la aprobación del usuario.
4. Rama. `git checkout -b issue-$issue` y un sufijo corto descriptivo.
5. Implementar siguiendo CLAUDE.md y `.claude/rules/`.
6. Tests. Delega al subagente `escritor-tests` un test por criterio de aceptación.
   Luego corre la suite completa.
7. Revisar. Delega al subagente `revisor-seguridad`. Corrige lo de severidad alta.
8. Publicar. Commit convencional que mencione #$issue, `git push -u origin HEAD`
   y crea el PR con las herramientas MCP de `github`. Cuerpo del PR:
   resumen, cómo se probó, hallazgos de la revisión, pendientes para humanos y `Closes #$issue`.
9. Termina con el enlace del PR y una tabla: criterio → estado.

La description está en inglés porque se carga en cada turno; el cuerpo en español porque solo se carga al invocarla. git push no está en allowed-tools a propósito: como en settings.json está en ask, Claude tendrá que pedir permiso en vivo.

- Un test por criterio de aceptación, con nombre Metodo_Escenario_Resultado.
- Cubre los casos límite: 404, 403 sin política, pageSize > 50, lista vacía.
- Corre `dotnet test` y reporta: tests creados, resultado, cobertura de criterios.
- No modifiques código de producción; si un test revela un bug, repórtalo.

Eres un especialista en tests para NestJS.
- Tests con Vitest + Supertest; sigue los patrones de los *.spec.ts existentes.
- Un test por criterio de aceptación, en forma "debe … cuando …".
- Cubre los casos límite: 404, 403 sin rol, pageSize > 50, lista vacía.
- Corre `pnpm --filter api test` y reporta: tests creados, resultado, cobertura de criterios.

El subagente revisor-seguridad es el de la sesión 5 (Opus, sin permisos de edición). Los hooks y el settings.json también son los de las sesiones 4 y 5.

Plan B

  • El MCP de GitHub no autenticaRevisa GITHUB_PAT y /mcp reconnect. Si sigue fallando, pide a Claude que use gh issue view 1 y gh pr create. Explica que el resultado es el mismo con otra integración.
  • El modelo va lento o hay límite de usoclaude -r "demo-ensayo" --fork-session y recorre la sesión ya hecha. También sirve para mostrar cómo se retoma trabajo.
  • Claude no toca el archivo de producciónPídelo directo: "aplica también el cambio del timeout". El bloqueo se ve igual.
  • Los tests tardan demasiadoAntes de la demo, deja en CLAUDE.md el comando que corre solo el proyecto de tests afectado.
  • La GitHub Action tardaMuestra el PR del ensayo donde ya corrió y vuelve al final de la sesión.
  • Se cae la redGraba el segundo ensayo en video y tenlo listo.

Variante con interfaz (opcional, +8 min)

Si el equipo tiene front, empieza en Claude Design: prototipa la pantalla "Reembolsos del pedido" con el design system del equipo, compártela en modo comentario y lleva el paquete de handoff a Claude Code. Luego el flujo sigue igual con un segundo issue para el front. Esto muestra el circuito completo diseño → código → PR.

Después de la demo: que cada persona repita el flujo con un issue real propio usando la misma skill. Es la mejor forma de comprobar que el programa funcionó.
