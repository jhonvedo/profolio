MCP en Claude Code

Terminal
# Servidor remoto (HTTP) compartido con el equipo vía .mcp.json
claude mcp add --transport http --scope project notion https://mcp.notion.com/mcp
# (se autentica con OAuth desde /mcp; si el servidor usa token, ponlo en .mcp.json con ${VAR}, ver abajo)

# Servidor local (stdio); todo después de -- se pasa al servidor
claude mcp add --transport stdio --env DB_URL=postgres://localhost/dev db -- npx -y <paquete-mcp-de-postgres>

claude mcp list          # estado de todos
claude mcp remove db
ScopeDónde se guardaCompartido
local (por defecto)~/.claude.json, solo este proyectoNo
project.mcp.json en la raíz del repoSí, por git
user~/.claude.json, todos tus proyectosNo
.mcp.json
{
  "mcpServers": {
    "docs-internas": {
      "type": "http",
      "url": "${DOCS_MCP_URL:-https://mcp.interno.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_MCP_TOKEN}" }
    }
  }
}
  • ${VAR} y ${VAR:-valor} se expanden desde el entorno: los secretos nunca van en el archivo.
  • Los servidores de .mcp.json piden aprobación la primera vez que abres el repo.
  • Los conectores de claude.ai (los que habilitó el admin) aparecen solos en Claude Code si inicias sesión con claude.ai. /mcp los muestra y permite autenticar.
  • Cada servidor MCP añade herramientas al contexto. Conecta los que el equipo usa, no todos los que existen.
Stack Azure: para equipos .NET suele valer la pena un servidor MCP de Azure DevOps o de Azure (work items, pipelines, recursos). Revisa que venga de una fuente confiable y dale el mínimo de permisos.

Conectores en claude.ai

  • El admin habilita cada conector y puede dejar sus acciones en solo lectura, con aprobación o bloqueadas.
  • Conectores propios (servidores MCP remotos): solo los Owners los agregan en Team/Enterprise. La conexión sale desde la nube de Anthropic, así que el servidor debe ser accesible desde internet o permitir las IPs de Anthropic.
  • Con autorización de toda la organización (Okta), el admin autoriza una vez y los miembros heredan el acceso.

Plugins: distribuir la configuración del equipo

Un plugin empaqueta skills, subagentes, hooks y servidores MCP para instalarlos con un comando. Un marketplace es un repo con un catálogo de plugins. Así la configuración de la sesión 5 llega a todos los repos sin copiar archivos.

Estructura de un plugin
plataforma-tools/
├── .claude-plugin/plugin.json   # { "name", "description", "version" }
├── skills/nueva-migracion/SKILL.md
├── agents/revisor-seguridad.md
├── hooks/hooks.json
└── .mcp.json
.claude-plugin/marketplace.json (repo del marketplace)
{
  "name": "empresa-tools",
  "owner": { "name": "Equipo Plataforma" },
  "plugins": [
    { "name": "plataforma-tools", "source": "./plugins/plataforma-tools",
      "description": "Skills, hooks y agentes del equipo" }
  ]
}
.claude/settings.json de cada repo
{
  "extraKnownMarketplaces": {
    "empresa-tools": { "source": { "source": "github", "repo": "mi-org/claude-plugins" } }
  },
  "enabledPlugins": { "plataforma-tools@empresa-tools": true }
}

Manualmente: /plugin marketplace add mi-org/claude-plugins y /plugin install plataforma-tools@empresa-tools. Las skills del plugin se invocan como /plataforma-tools:nueva-migracion. Si el repo del marketplace es privado, cada desarrollador necesita acceso de lectura a él en GitHub.

GitHub: @claude en issues y PRs

La forma rápida es /install-github-app dentro de Claude Code (requiere gh autenticado y ser admin del repo): instala la GitHub App, crea el secreto y abre un PR con el workflow. Después, cualquiera con permiso de escritura escribe @claude en un issue o PR.

.github/workflows/claude.yml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 15"
  • Con suscripción en vez de API key: claude setup-token genera un token; úsalo como claude_code_oauth_token. Para toda la organización, mejor una API key de Console o federación OIDC (el token queda atado a quien lo generó).
  • Con prompt: la acción corre sin mención (en cada PR, en un cron). Puede invocar skills del repo: prompt: "/nombre-skill".
  • Si usan Azure DevOps o GitLab, usen Claude Code en modo headless dentro del pipeline (abajo).

Gobierno: managed settings

Los managed settings tienen la máxima prioridad: ningún usuario ni repo puede anularlos. Se despliegan por MDM, archivo de sistema o desde la consola de administración. También existe un CLAUDE.md de política en /Library/Application Support/ClaudeCode/ (macOS), /etc/claude-code/ (Linux/WSL) o C:\Program Files\ClaudeCode\ (Windows).

managed-settings.json (ejemplo)
{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(//**/.env)",
      "Read(~/.ssh/**)",
      "Read(~/.azure/**)",
      "Bash(az keyvault secret show *)"
    ]
  },
  "forceLoginMethod": "claudeai"
}
  • allowManagedPermissionRulesOnly hace que solo cuenten las reglas del admin.
  • forceLoginOrgUUID obliga a usar la cuenta de la organización.
  • Las skills, subagentes y hooks de managed settings tienen prioridad sobre los de usuario y repo.

Proyecto final · Kit de Claude del equipo

90 min + demo
  1. Crea el repo claude-plugins de la organización con un marketplace y un plugin que incluya las skills, hooks y subagentes de la sesión 5.

  3. Agrega un servidor MCP útil al .mcp.json (tracker de issues o documentación interna).
  4. Instala la GitHub Action y resuelve un issue real con @claude de principio a fin.
  5. Propón al admin un managed-settings.json con los deny de la organización.
  6. Demo de 10 minutos: flujo completo desde Claude Design o un issue hasta el PR revisado.
