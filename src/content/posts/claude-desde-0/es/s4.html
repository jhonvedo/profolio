La carpeta .claude

Estructura recomendada del repo
mi-repo/
├── CLAUDE.md                 # instrucciones del equipo (commit)
├── CLAUDE.local.md           # personales (gitignore)
├── .mcp.json                 # servidores MCP del equipo (commit)
└── .claude/
    ├── settings.json         # permisos, hooks, env, modelo (commit)
    ├── settings.local.json   # overrides personales (gitignore)
    ├── rules/                # reglas por ruta
    │   ├── api.md
    │   └── testing.md
    ├── skills/               # /comandos y procedimientos
    │   └── nueva-migracion/SKILL.md
    ├── agents/               # subagentes
    │   └── revisor-seguridad.md
    └── hooks/                # scripts que llaman los hooks
        ├── proteger-archivos.sh
        └── formatear.sh

En tu máquina, ~/.claude/ tiene la misma estructura para lo personal (settings, CLAUDE.md, rules, skills, agents), además de la memoria automática por proyecto y el historial.

CLAUDE.md que funciona

  • Menos de 200 líneas. Archivos largos consumen contexto y bajan la adherencia. Mueve el detalle a reglas por ruta.
  • Lo que Claude no puede descubrir solo: comandos exactos, decisiones y su porqué, trampas conocidas. No copies lo que ya dice el código.
  • Concreto y verificable: "Usa Result<T> para errores de negocio" es mejor que "maneja bien los errores".
  • Sin contradicciones: si dos reglas chocan, Claude elige una al azar.
  • Empieza con /init: analiza el repo y genera un borrador; si ya existe un CLAUDE.md, propone mejoras en vez de sobrescribirlo. Con CLAUDE_CODE_NEW_INIT=1 el flujo es interactivo y también propone skills y hooks. Si el equipo viene de Codex, Gemini CLI o Cursor, /import trae esa configuración (y /init lo ofrece si la encuentra).
  • Audítalo de vez en cuando: /doctor prompt-audit busca instrucciones contradictorias, obsoletas o que mencionan archivos y comandos que ya no existen. Propone cambios, pero no los aplica sin que se lo pidas.
CLAUDE.md · API .NET
# Orders API

## Stack
- .NET 8, ASP.NET Core Minimal APIs, EF Core 8 (SQL Server), MediatR
- Tests: xUnit + FluentAssertions + Testcontainers

## Comandos
- Build: `dotnet build Orders.sln`
- Tests: `dotnet test Orders.sln --no-build`
- Formato: `dotnet format Orders.sln --verify-no-changes`
- Nueva migración: `dotnet ef migrations add <Nombre> -p src/Orders.Infrastructure -s src/Orders.Api`

## Arquitectura
- Clean Architecture: Api → Application → Domain. Infrastructure implementa interfaces de Application.
- Domain no referencia EF Core ni ASP.NET Core.

## Convenciones
- Async de punta a punta; propaga `CancellationToken`.
- Errores de negocio con `Result<T>`; excepciones solo para lo inesperado.
- Nunca edites una migración ya aplicada: crea una nueva.
- Configuración sensible solo por User Secrets o Key Vault; nunca en appsettings.

## Antes de terminar una tarea
- Corre build, tests y formato. Si algo falla, arréglalo antes de reportar.

@docs/adr/README.md

Importar otros archivos

@ruta/archivo dentro de un CLAUDE.md carga ese archivo al inicio (rutas relativas al archivo que importa, hasta 4 niveles de anidación). Para mencionar una ruta sin importarla, ponla entre backticks. Los imports fuera del repo piden aprobación la primera vez.

Cómo se cargan

Claude Code carga CLAUDE.md y CLAUDE.local.md del directorio actual y de todos los superiores; se concatenan, no se sobreescriben. Los de subdirectorios se cargan cuando Claude lee archivos ahí. En monorepos, claudeMdExcludes evita cargar los de otros equipos. Si el repo solo tiene AGENTS.md, Claude lo lee como instrucciones del proyecto.

Reglas por ruta

Son instrucciones con alcance: un archivo de .claude/rules/ con paths en su encabezado solo se carga cuando Claude lee archivos que coinciden, así que no gasta contexto el resto del tiempo.

.claude/rules/endpoints.md
---
paths:
  - "src/Orders.Api/Endpoints/**/*.cs"
---
# Reglas para endpoints
- Cada endpoint en su propia clase estática con `MapXxx(this IEndpointRouteBuilder)`.
- Valida con FluentValidation; responde errores con `Results.ValidationProblem`.
- Devuelve `TypedResults` para que OpenAPI documente las respuestas.
- Autorización explícita: `.RequireAuthorization("policy")`.
.claude/rules/testing.md
---
paths:
  - "**/*.{spec,test}.ts"
  - "apps/web/e2e/**/*.ts"
---
# Reglas para tests
- Un `describe` por unidad; nombres en forma "debe … cuando …".
- Nada de `setTimeout` en tests: usa fake timers de Vitest.
- En e2e, selecciona por rol o `data-testid`, nunca por clases CSS.
- Mockea solo en los bordes (HTTP, DB); no mockees el código propio.

Auto memory

Claude guarda notas propias mientras trabaja: tus preferencias, correcciones que le das, decisiones del proyecto y dónde encontrar cosas fuera del repo. Viven en ~/.claude/projects/<proyecto>/memory/ y se cargan al inicio (primeras 200 líneas). Se administra con /memory, que también abre los CLAUDE.md para editarlos. Se puede apagar con "autoMemoryEnabled": false.

Regla del equipo. Si le corriges algo a Claude dos veces, no confíes en la memoria automática: agrégalo al CLAUDE.md o a una regla para que todo el equipo lo tenga.

settings.json: capas y permisos

Orden de precedencia, de mayor a menor: managed settings (organización) → flags de CLI → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json.

Cómo se evalúan los permisos: primero deny, luego ask, luego allow. La primera coincidencia gana y un deny en cualquier capa no se puede anular con un allow.
.claude/settings.json · .NET
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(dotnet build *)",
      "Bash(dotnet test *)",
      "Bash(dotnet format *)",
      "Bash(dotnet ef migrations add *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(dotnet ef database update *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(**/appsettings.Production.json)",
      "Read(~/.microsoft/usersecrets/**)",
      "Read(~/AppData/Roaming/Microsoft/UserSecrets/**)",
      "Bash(dotnet nuget push *)"
    ]
  },
  "env": { "DOTNET_CLI_TELEMETRY_OPTOUT": "1" }
}
.claude/settings.json · Node
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(pnpm test *)",
      "Bash(pnpm lint *)",
      "Bash(pnpm -r typecheck)",
      "Bash(pnpm --filter api test *)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(pnpm add *)",
      "Bash(pnpm --filter api prisma migrate *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(**/secrets/**)",
      "Bash(npm publish *)",
      "Bash(pnpm publish *)"
    ]
  }
}

Sintaxis de reglas

  • Bash(git log *): el * va después del subcomando. Bash(git *) permitiría todo git, incluido push.
  • Read/Edit usan patrones estilo gitignore: ./ruta relativa al directorio actual, /ruta relativa al archivo de settings, ~/ruta desde tu home, //ruta absoluta.
  • WebFetch(domain:learn.microsoft.com), mcp__github__create_issue, Agent(nombre).
  • En Windows, Claude corre los comandos con la herramienta PowerShell (activa por defecto con cuentas de claude.ai) y las reglas Bash(...) no la cubren. Repite las importantes con la misma forma: PowerShell(dotnet test *), PowerShell(dotnet nuget push *). Las reglas Read y Edit valen igual.
  • Las reglas de Bash que intentan restringir argumentos son frágiles (curl con distintas opciones). Para garantías reales usa hooks o el sandbox.
  • /permissions las muestra y edita; /fewer-permission-prompts analiza tus sesiones y sugiere un allowlist.

Sandbox: la garantía del sistema operativo

Las reglas de permisos deciden qué herramientas usa Claude. El sandbox trabaja un nivel más abajo: el sistema operativo limita qué archivos y qué dominios de red pueden tocar los comandos de Bash y todos sus procesos hijos, incluido un script de Python o Node que abre archivos por su cuenta, que una regla Read(...) no alcanza.

  • Activarlo: /sandbox abre el panel y muestra si falta alguna dependencia. Para todos tus proyectos, "sandbox": { "enabled": true } en ~/.claude/settings.json. El admin puede imponerlo desde managed settings.
  • Por defecto: los comandos solo escriben en la carpeta del proyecto, en un directorio temporal y en las carpetas agregadas con /add-dir. La red queda limitada a los dominios que apruebes.
  • Secretos: sandbox.filesystem.denyRead bloquea rutas para cualquier proceso. Combínalo con las reglas Read(...) de arriba, que cubren las herramientas propias de Claude.
  • Dónde funciona: macOS, Linux y WSL2. No funciona en Windows nativo: un equipo .NET en Windows que lo quiera usar debe correr Claude Code dentro de WSL2. En Linux y WSL2 requiere bubblewrap y socat.
Según el modo que elijas en /sandbox, los comandos que respetan esos límites corren sin pedir permiso. Por eso encaja con el modo auto y con tareas largas: menos interrupciones y un límite que no depende de lo que decida el modelo.

Recetas de settings.json

Hasta aquí vimos permisos. Pero settings.json sirve para mucho más: avisos, barra de estado, modelo por defecto, variables de entorno, cómo te autenticas. Estas recetas son las más útiles en el día a día.

Casi todas son personales: van en ~/.claude/settings.json (tu carpeta de usuario) y aplican a todos tus repos. Cuando una receta tiene sentido para todo el equipo, lo indico.

En la sesión solo se configuran el aviso y la barra de estado. El resto de las recetas es referencia para cuando lo necesites. Los comentarios // de los ejemplos son explicativos: bórralos en el archivo real.

Aviso cuando Claude termina o necesita permiso

El problema: le das una tarea a Claude, cambias de ventana y no te enteras de que lleva cinco minutos esperando tu aprobación. Claude Code ya manda un aviso de escritorio, pero solo en Ghostty, Kitty y iTerm2. En otras terminales (Windows Terminal, la de VS Code) hay dos opciones: "preferredNotifChannel": "terminal_bell" para que suene la campana, o dos hooks con el sonido o aviso que prefieras:

  • Notification se dispara cuando Claude necesita tu atención: un permiso pendiente o una espera larga.
  • Stop se dispara cada vez que Claude termina de responder.
~/.claude/settings.json · Windows (sonido, sin instalar nada)
{
  "hooks": {
    "Notification": [
      { "matcher": "permission_prompt|idle_prompt",
        "hooks": [{ "type": "command",
          "command": "powershell.exe -NoProfile -Command \"[System.Media.SystemSounds]::Exclamation.Play()\"" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
          "command": "powershell.exe -NoProfile -Command \"[System.Media.SystemSounds]::Asterisk.Play()\"" }] }
    ]
  }
}

Dos sonidos distintos: uno cuando espera permiso y otro cuando termina. Así sabes sin mirar si tienes que volver.

Windows con notificación visual (módulo BurntToast)
# Una sola vez, en PowerShell:
Install-Module BurntToast -Scope CurrentUser

# Luego, en el hook de settings.json:
"command": "powershell.exe -NoProfile -Command \"New-BurntToastNotification -Text 'Claude Code','Necesita tu atención'\""
macOS y Linux: la línea "command" del hook
// macOS
"command": "osascript -e 'display notification \"Necesita tu atención\" with title \"Claude Code\" sound name \"Glass\"'"

// Linux
"command": "notify-send 'Claude Code' 'Necesita tu atención'"
Va en tu configuración personal, no en el repo. El comando depende del sistema operativo y cada persona prefiere avisos distintos. Para probarlo, pide a Claude algo que requiera permiso y cambia de ventana.

Barra de estado

Una línea debajo del prompt que siempre muestra lo importante: modelo, carpeta, rama y cuánto contexto llevas. Claude Code ejecuta tu script cada vez que cambia algo y le pasa los datos de la sesión como JSON.

La forma rápida es pedírsela a Claude: /statusline muestra modelo, rama de git y % de contexto. Él genera el script y lo registra. Si prefieres hacerlo a mano:

~/.claude/statusline.sh
#!/usr/bin/env bash
# Claude Code envía los datos de la sesión por stdin, en JSON.
INPUT=$(cat)
MODEL=$(echo "$INPUT" | jq -r '.model.display_name')
CWD=$(echo "$INPUT" | jq -r '.workspace.current_dir')
CTX=$(echo "$INPUT" | jq -r '.context_window.used_percentage // 0')
BRANCH=$(git -C "$CWD" branch --show-current 2>/dev/null)
DIR="${CWD//\\//}"; DIR="${DIR##*/}"   # nombre de la carpeta; también con rutas de Windows

echo "[$MODEL] $DIR ${BRANCH:+on $BRANCH} · ${CTX}% contexto"
~/.claude/settings.json
{
  "statusLine": {
    "type": "command",
    "command": "bash ~/.claude/statusline.sh"
  }
}

Resultado: [Sonnet 5.5] orders-api on PAY-482 · 34% contexto. Cuando el porcentaje pase de 70–80%, es buen momento para /compact o /clear. Necesita jq instalado.

Usar una API key en vez de la suscripción

Por defecto Claude Code usa tu cuenta de claude.ai y consume la cuota del plan. Puedes usar en cambio una API key de la Claude Console, que se cobra por tokens. Tiene sentido para pipelines de CI, scripts, o si tu empresa factura el uso por API.

Opción 1 · variable de entorno
# PowerShell (solo esta terminal)
$env:ANTHROPIC_API_KEY = "sk-ant-..."

# bash / zsh
export ANTHROPIC_API_KEY="sk-ant-..."

claude   # usa la API key en vez de la cuenta
Opción 2 · apiKeyHelper en ~/.claude/settings.json
{
  // Un script que imprime la key. Así no queda escrita en ningún archivo.
  "apiKeyHelper": "~/.claude/get-api-key.sh"
}

El script puede leer la key de tu gestor de contraseñas o de un vault de la empresa. Es la opción más segura y la que conviene para equipos.

Si la empresa usa Amazon Bedrock o Google Vertex
# Bedrock: usa tus credenciales de AWS
export CLAUDE_CODE_USE_BEDROCK=1
export AWS_REGION=us-east-1

# Vertex AI: usa tus credenciales de Google Cloud
export CLAUDE_CODE_USE_VERTEX=1
export CLOUD_ML_REGION=us-east5
export ANTHROPIC_VERTEX_PROJECT_ID=mi-proyecto
Nunca pongas una API key en .claude/settings.json del repo ni en ningún archivo que se suba a git. Si el admin fijó forceLoginMethod en managed settings, la API key puede no estar permitida: consulta antes.
