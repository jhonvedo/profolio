Cada mensaje que envías hace que Claude Code le mande al modelo todo el contexto acumulado. Por eso el consumo depende menos de cuánto escribes y más de cuánto contexto arrastras. La meta no es gastar lo mínimo a cualquier precio, sino no pagar por tokens que no aportan: un contexto pequeño y relevante es más barato y da mejores respuestas.

Cómo medirlo

  • /contextQué ocupa el contexto ahora y cuánto queda: memoria, MCP, skills, historial.
  • /usageTokens y costo de la sesión. En Pro, Max, Team y Enterprise muestra además qué parte del consumo reciente vino de cada skill, subagente, plugin y servidor MCP, y avisa cuando algo (contexto largo, fallos de caché) pasa del 10%.
  • Barra de estadoEl % de contexto siempre a la vista (sesión 4).
  • count_tokensEndpoint de la API que cuenta un texto antes de enviarlo.
Mide antes de optimizar. Una semana mirando /usage dice más que cualquier regla general: muestra si lo que pesa es un MCP, una skill, los subagentes o sesiones que nunca se limpian.

Lo que conviene saber

  • Caché: lo que se repite en cada turno se reutiliza desde caché y cuesta menos, pero igual ocupa espacio. Dura una hora en una suscripción y, por defecto, cinco minutos con API key: al volver de una pausa larga, el primer mensaje reprocesa todo el contexto.
  • Salida: cuesta más que la entrada, y el razonamiento cuenta como salida.
  • Autocompactación: cuando el contexto se acerca al límite, Claude Code lo resume solo y se pierden detalles. Mejor decidir tú cuándo.
  • /compact no es gratis: lee toda la conversación para resumirla. /clear no cuesta nada.
  • Los subagentes ahorran contexto, no consumo: sus peticiones también cuentan contra tu plan. Por eso conviene darles un modelo más chico.

.claude/hooks/solo-fallas.sh · PreToolUse con matcher "Bash"
#!/usr/bin/env bash
# Si el comando corre tests, deja pasar a Claude solo las fallas.
# Adaptado del ejemplo de la documentación oficial de costos.
INPUT=$(cat)
CMD=$(echo "$INPUT" | jq -r '.tool_input.command')
if [[ "$CMD" =~ ^(dotnet\ test|pnpm\ (-r\ |--filter\ [^\ ]+\ )?test) ]]; then
  FILTRADO="$CMD 2>&1 | grep -i -A 5 -E '(fail|error)' | head -100; echo '(salida filtrada: solo fallas)'"
  echo "$INPUT" | jq --arg c "$FILTRADO" \
    '{hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "allow", updatedInput: (.tool_input + {command: $c})}}'
else
  echo "{}"
fi

El hook reescribe el comando antes de que corra: Claude ve hasta 100 líneas alrededor de las fallas en vez de toda la salida. Regístralo en .claude/settings.json bajo PreToolUse con "matcher": "Bash", como los hooks de la sesión 5. En Windows, cuando Claude corre los tests con la herramienta PowerShell, este hook no se dispara: está escrito para bash.

Qué es un plugin LSP y por qué ahorra tokens

Tu IDE sabe dónde está definido cada método porque usa un servidor de lenguaje (LSP): es el motor detrás de F12, «Ir a definición» y «Buscar referencias». Claude Code no lo trae por defecto, así que para encontrar un método busca texto: corre un grep, encuentra diez coincidencias (comentarios, tests, nombres parecidos) y abre varios archivos hasta dar con el correcto. Cada archivo abierto son tokens.

Con el plugin, Claude le pregunta al servidor de lenguaje y recibe la ruta y la línea exactas. De paso, ve los errores de compilación apenas edita un archivo, sin esperar al build.

Instalar el plugin de tu lenguaje
# 1. Una vez por máquina: el servidor de lenguaje
dotnet tool install --global csharp-ls                 # .NET
npm i -g typescript-language-server typescript         # Node / TypeScript

# 2. En Claude Code: el plugin del marketplace oficial
/plugin install csharp-lsp@claude-plugins-official
/plugin install typescript-lsp@claude-plugins-official

# 3. Pregunta como siempre; Claude usa el servidor de lenguaje cuando le sirve
