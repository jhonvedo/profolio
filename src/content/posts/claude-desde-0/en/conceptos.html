Before configuring anything, the team needs a shared vocabulary. These are the pieces everything else is built from, explained with a dev-team analogy.

Which piece do I need? Quick questions

  • "Claude should always know this about the repo"CLAUDE.md (or a rule with paths if it only applies to certain files)
  • "This takes 6 steps and is always done the same way"Skill
  • "This has to happen every time, without relying on Claude remembering"Hook (for example, formatting after every edit)
  • "This must never happen"deny rule (for example, reading the .env or publishing the package)
  • "I need someone to review/research without cluttering my session"Subagent
  • "Claude needs to see data from Jira, GitHub, the DB or internal docs"MCP / connector
  • "I want 12 repos to have the same setup"Plugin in a team marketplace

Hook or deny: what doesn't depend on Claude remembering

Claude Code enforces both, not the model, so they work even if Claude forgets an instruction. But they solve opposite problems: a hook makes something happen at a fixed point; a deny rule blocks an action.

.claude/settings.json · a hook and a deny rule
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(npm publish *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh" }] }
    ]
  }
}

With this, Claude can't read the .env files or publish the package even if asked, and every file it edits gets formatted automatically. deny rules are covered in depth in session 4, and hooks, with events and more examples, in session 5.

Tokens: the unit everything is measured in

Claude doesn't read words or characters: it reads tokens, chunks of text that can be a short word, part of a long word, a symbol or a space. Everything that goes into the model and everything that comes out is counted in tokens, and that unit measures three things: how much fits in the context, how much a task costs, and how much of the plan's quota you use.

Illustrative example · the same text in tokens
# Spanish: 6 words ≈ 10 tokens
Claude refactorizó el servicio de reembolsos
[Claude][ ref][actor][izó][ el][ servicio][ de][ re][emb][olsos]

# English: 5 words ≈ 6 tokens
Claude refactored the refunds service
[Claude][ refactor][ed][ the][ refunds][ service]

The split is illustrative: Anthropic doesn't publish how its tokenizer cuts text. What does hold: common English words are usually a single token, long words or words in other languages get split into pieces, and the space sticks to the next word. For an exact count, use count_tokens.

What surprises people at first: the model doesn't remember between messages. Every time you write, Claude Code sends it the whole accumulated context again: instructions, CLAUDE.md, files read and history. That's why a long session with mixed topics gets slower and more expensive with every turn. Caching makes what repeats cheaper, but it still takes up space and still costs.

What loads on every turn, how to measure it and how to save tokens without losing quality has its own chapter: Consumption and efficiency.

Available models and their consumption

How much each model consumes per token, with Haiku 5.5 as the baseline (October 2026):

ModelConsumption per tokenDefault effortWhat for
Haiku 5.51×mediumShort, high-volume tasks and search subagents.
Sonnet 5.520×mediumDay-to-day work: features, tests, explaining code.
Opus 5.540×mediumComplex work. Claude Code's default model.
Fable 5.1100×highThe hardest work: architecture, complex bugs.

Watch Haiku 5.5 in long sessions: once the prompt passes 100,000 tokens, it costs 5 times more. In Claude Code that comes fast, because every turn sends the whole context; there Haiku 5.5 sits at 5× and Sonnet only 4 times above it. On Bedrock and Vertex, the haiku alias still points to Haiku 4.5, which costs 10×.

Effort multiplies on top of this: more effort means more reasoning, and reasoning is billed as output, which costs 5 times input. There's no fixed multiplier per level; measure it with /usage. Prices on the official page.

Model and effort: concrete examples

Two independent knobs. The model sets how much capability there is; effort sets how much of that capability each response uses. More of either means slower answers and more of the plan's quota.

In Claude Code the default model is Opus 5.5 at medium effort (each model's values are in the table above). Here's how to pick them by task:

SituationModelEffortWhy
"How do I do a GroupBy in LINQconditional type in TS?", renaming, formattingSonnet 5.5 or Haiku 5.5lowKnown answer; thinking longer doesn't help.

Typical sprint feature: endpoint + validation + testsSonnet 5.5 or Opus 5.5highSeveral files and small decisions.
Intermittent bug, race condition, deadlock, memory leakOpus 5.5 or Fable 5.1xhighHypotheses need to be formed and ruled out.
Architecture design or migration (.NET Framework → .NET 8Express → NestJS, CJS → ESM)Fable 5.1xhigh–max in Plan modeLong-term trade-offs; a mistake costs weeks.
Large but repetitive refactor (100 files, same pattern)opusplanhighOpus designs the plan, Sonnet executes it more cheaply.

How to change them in Claude Code

/model opens the picker (← → adjust effort).
/effort xhigh changes only the effort.
claude --model sonnet --effort low at startup.
Type ultrathink in a prompt to reason more for that turn only.
In subagents and skills: model: and effort: in the frontmatter.
CLAUDE_CODE_SUBAGENT_MODEL=haiku sets the default subagent model.

Common mistakes

Leaving max on for everything: burns quota and can "overthink" simple tasks.
Using Haiku for design: you save tokens and lose hours fixing things.
Switching models mid-way through a long task for no reason: the new model rereads the whole context.
Blaming the model when context was missing: the problem is almost always the prompt or CLAUDE.md.

Which language should you write to Claude in?

Claude understands and answers very well in Spanish and many other languages. For non-English-speaking teams, the real question is about token cost and consistency.

What the measurements say

  • The tokenizer splits text into chunks and is optimized for English. A measurement with the official count_tokens endpoint (Sonnet 4.6, June 2026) gave 1.16 tokens per word in English and 1.72 in Spanish, about 48% more for the same content.
  • Another analysis of ~2,000 real Claude Code sessions found Spanish prompts 44% to 63% more expensive (average ~54%)… but prompts were only ~10% of the total context. The rest is code, files read and tool output, which don't change with the language. The real overhead ended up around 5%, with no noticeable quality difference on coding tasks.
  • The ratio varies between models because they don't all use the same tokenizer. These are one-off measurements, not official Anthropic figures: repeat them with your team's own text using count_tokens, or compare /context and /usage in real sessions.
