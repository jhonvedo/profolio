Rule of thumb: if something must always happen (formatting, blocking secrets, running tests), it's a hook. If it's "how we do X", it's a skill or a rule.

Hooks

Main events

There are more events (PostToolUseFailure, ConfigChange, FileChanged, InstructionsLoaded, WorktreeCreate, TaskCompleted…). The full reference is in the hooks documentation.

Anatomy

Configuration shape
{
  "hooks": {
    "EventName": [
      {
        "matcher": "Edit|Write",         // which tool; empty = all
        "hooks": [
          {
            "type": "command",           // also: http, mcp_tool, prompt, agent
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/x.sh",
            "if": "Edit(*.cs)",           // optional filter using permission syntax
            "timeout": 60                  // seconds
          }
        ]
      }
    ]
  }
}

The // comments are for explanation only: JSON doesn't allow comments in the real file.

Input

JSON on stdin: session_id, cwd, hook_event_name, tool_name, tool_input (e.g. tool_input.file_path, tool_input.command).

Exit 0

All good. On SessionStart and UserPromptSubmit, stdout is added as context for Claude.

Exit 2

Blocks. stderr is used as the reason and Claude reads it. Other codes are non-blocking errors.

For fine control, print JSON to stdout. The values of permissionDecision are allow, deny or ask. Event-specific fields go inside hookSpecificOutput; if you put them at the top level, they're silently ignored.

JSON output from a hook
// PreToolUse: decide for the tool
{ "hookSpecificOutput": { "hookEventName": "PreToolUse",
    "permissionDecision": "deny", "permissionDecisionReason": "…" } }

// Stop: don't let it finish
{ "decision": "block", "reason": "…" }

Hook 1 · Protect sensitive files (PreToolUse)

.claude/hooks/protect-files.sh
#!/usr/bin/env bash
# Blocks edits to files that only humans should change.
INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
FILE="${FILE//\\//}"   # normalize Windows paths

# Templates like .env.example can be edited.
[[ "$FILE" == *.example ]] && exit 0

PROTECTED=("*/.env" "*/.env.*" "*/.git/*" "*/appsettings.Production.json" "*/Migrations/*""*/pnpm-lock.yaml" "*/prisma/migrations/*")

for p in "${PROTECTED[@]}"; do
  if [[ "$FILE" == $p ]]; then   # $p unquoted: matched as a pattern
    echo "Blocked: $FILE is a protected file ($p). Migrations are generated with dotnet ef.Use the pnpm/prisma commands." >&2
    exit 2
  fi
done
exit 0

Hook 2 · Format after editing (PostToolUse)

.claude/hooks/format.sh · .NET
#!/usr/bin/env bash
FILE=$(jq -r '.tool_input.file_path // empty')
FILE="${FILE//\\//}"; ROOT="${CLAUDE_PROJECT_DIR//\\//}"
case "$FILE" in
  *.cs)
    # Only the edited file, without loading the solution or building
    cd "$ROOT" && dotnet format whitespace . --folder --include "${FILE#"$ROOT"/}" >/dev/null 2>&1 ;;
esac
exit 0

dotnet format on the whole solution loads it through MSBuild on every edit, and over a long task that adds up to minutes. whitespace --folder fixes only the edited file's formatting, without building. Full formatting (style and analyzers) is checked at the end with the command in CLAUDE.md.

.claude/hooks/format.sh · Node
#!/usr/bin/env bash
FILE=$(jq -r '.tool_input.file_path // empty')
case "$FILE" in
  *.ts|*.tsx|*.js|*.json|*.md)
    cd "$CLAUDE_PROJECT_DIR" && pnpm exec prettier --write "$FILE" >/dev/null 2>&1
    pnpm exec eslint --fix "$FILE" >/dev/null 2>&1 ;;
esac
exit 0

Hook 3 · Don't finish with failing tests (Stop)

.claude/hooks/green-tests.sh
#!/usr/bin/env bash
INPUT=$(cat)
# Avoid loops: if we already forced it to continue once, let it finish.
if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then exit 0; fi

cd "$CLAUDE_PROJECT_DIR"
# No changes (including new files): nothing to verify.
[ -z "$(git status --porcelain)" ] && exit 0

# If the code hasn't changed since the tests last passed, don't rerun them.
HASH=$( { git diff HEAD; git ls-files -o --exclude-standard -z | xargs -0 -r cat; } 2>/dev/null | git hash-object --stdin )
STAMP="$(git rev-parse --git-dir)/claude-tests-ok"
[ "$(cat "$STAMP" 2>/dev/null)" = "$HASH" ] && exit 0

if ! OUT=$(dotnet test --nologo -v qpnpm -r test 2>&1); then
  echo "Tests are failing. Fix them before finishing:" >&2
  echo "$OUT" | tail -n 40 >&2
  exit 2
fi
echo "$HASH" > "$STAMP"
exit 0

The hook runs every time Claude finishes responding, even when it only answered a question. That's why it stores a fingerprint of the changes: if nothing changed since the tests last passed, it doesn't run them again.

Hook 4 · Context at startup (SessionStart)

.claude/hooks/context.sh
#!/usr/bin/env bash
cd "$CLAUDE_PROJECT_DIR"
echo "Current branch: $(git branch --show-current)"
echo "Recent commits:"; git log --oneline -5
exit 0

Registering them in .claude/settings.json

.claude/settings.json (hooks section)
{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|resume",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/context.sh" }] }
    ],
    "PreToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/green-tests.sh", "timeout": 300 }] }
    ]
  }
}
  • Make the scripts executable: chmod +x .claude/hooks/*.sh.
  • The desktop notification (Notification) doesn't go in this file: it depends on the operating system, so each person puts it in their ~/.claude/settings.json using the session 4 recipe.
  • /hooks shows the loaded hooks. claude --debug logs every run.
  • A hook that exits with code 2 blocks even if there's an allow rule; but a hook that says "allow" doesn't override a deny.
Security: hooks run commands with your permissions. Review a repo's hooks before trusting the folder, just as you would a postinstall script.

Skills

A skill is a folder with a SKILL.md (frontmatter + instructions) and, optionally, scripts and reference files. Claude only keeps each skill's description in context; the full content loads when it's used (progressive disclosure). They're invoked with /name, or Claude uses them on its own when the description fits.

The old commands in .claude/commands/*.md still work and are now equivalent to skills; for new work use .claude/skills/.

.claude/skills/new-migration/SKILL.md
---
description: Creates and validates an EF Core migration. Use it when the user changes entities or asks for a migration.
argument-hint: "[MigrationName]"
disable-model-invocation: true
allowed-tools: Bash(dotnet ef *) Bash(dotnet build *) Read Grep
---
## Current state
!`git status --short`

## Task
1. Check that the build passes: `dotnet build Orders.sln`.
2. Create the migration: `dotnet ef migrations add $ARGUMENTS -p src/Orders.Infrastructure -s src/Orders.Api`.
3. Read the generated file and report: affected tables/columns, possible data loss, indexes.
4. If there's a `DropColumn` or type change, stop and ask for confirmation.
5. Generate the idempotent script for review: `dotnet ef migrations script --idempotent`.
.claude/skills/new-endpoint/SKILL.md
---
description: Creates a complete NestJS endpoint (zod DTO, service, controller, tests). Use it when asked for a new endpoint in apps/api.
argument-hint: "[resource] [verb]"
arguments: [resource, verb]
allowed-tools: Bash(pnpm --filter api *) Read Grep Glob Edit Write
---
## Reference
Follow the pattern in [endpoint-example.md](endpoint-example.md).

## Task
Create the `$verb` endpoint for the `$resource` resource:
1. zod DTO in `apps/api/src/$resource/dto/`.
2. Service method with typed error handling.
3. Controller route with an authentication guard.
4. Service unit tests and an e2e test with Supertest.
5. Run `pnpm --filter api test` and `pnpm --filter api typecheck`.
  • descriptionWhat it does and when to use it. Claude decides based on this; write the main case first. Keep it in English: it loads on every turn, while the body only loads when the skill is used.
  • disable-model-invocation: trueOnly you invoke it (deploys, migrations, anything with side effects).
  • user-invocable: falseOnly Claude uses it (reference knowledge).
  • allowed-toolsTools pre-approved while it runs.
  • argument-hint, argumentsArguments: $ARGUMENTS, $0, $1 or $name.
  • context: fork + agentRuns the skill in a subagent that doesn't see your conversation and only returns the summary (see Skills and subagents).
  • paths, model, effortActivate by path; change the model or effort while the skill is active.

!`command` runs the command before the skill is sent and replaces the placeholder with the output, so Claude gets real data. Keep SKILL.md under 500 lines and move detail into supporting files. /skills lists the skills and /skill-doctor checks how much context they use.

Skills in claude.ai and in Claude Code: the same format works in both. Skills an admin provisions for the organization sync to Claude Code: you invoke them with /<name>, or with /anthropic-skills:<name> if another command uses that name.

Subagents

A subagent works in its own context and returns only the result, so the main session doesn't fill up with files it read. Claude Code ships with Explore (read-only search), Plan and general-purpose. You create your own with /agents or by hand:

.claude/agents/security-reviewer.md
---
name: security-reviewer
description: Reviews changes looking for vulnerabilities (injection, authz, secrets, deserialization). Use it before opening a PR that touches authentication, payments or personal data.
tools: Read, Grep, Glob, Bash
model: opus
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/read-only-git.sh"
---
You are a security reviewer for ASP.NET Core APIsNestJS APIs and Next.js apps.
1. Read `git diff main...HEAD`.
2. Check: input validation, per-resource authorization, parameterized queries,
   secrets in code or logs, CORS, error handling that leaks information.
3. Report only findings with evidence: file, line, risk, exploit scenario and fix.
4. Don't edit files or run commands that modify the repository.
.claude/hooks/read-only-git.sh
#!/usr/bin/env bash
# Read-only git only: no chaining, redirects or --output (which writes files).
CMD=$(jq -r '.tool_input.command // empty')
ALLOWED='^git (diff|log|show|status|blame)( |$)'
if [[ $CMD =~ $ALLOWED && $CMD != *[\;\&\|\<\>\`\$]* && $CMD != *--output* && $CMD != *$'\n'* ]]; then
  exit 0
fi
echo "The reviewer can only use git diff, log, show, status and blame." >&2
exit 2

Without Edit or Write it can't touch files, and the hook in its frontmatter only lets read-only git through: instruction 4 no longer depends on the model obeying. The tools field only takes tool names: Bash(git diff *) there limits nothing, and in disallowedTools it would remove Bash entirely. To limit specific commands you use a hook like this one.

  • Invoke it in natural language ("use the security-reviewer") or with @"security-reviewer (agent)".
  • Useful fields: tools/disallowedTools, model (sonnet, opus, haiku, fable, inherit), permissionMode, hooks, skills, mcpServers, memory, isolation: worktree, maxTurns.
  • Priority by name: managed → --agents → .claude/agents/ → ~/.claude/agents/ → plugins.
